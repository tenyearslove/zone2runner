DP1. 설명용이성 — 판단 근거를 그대로 설명하는 구조

설명이 실제 판단과 일치하도록 만드는 두 가지 설계안을 비교하고 선택한다.

DP1. 설계 문제 정의

3

1.배경

  • 이 앱은 심박을 보며 달리기를 실시간으로 코칭한다 — "지금 존을 벗어났어요", "속도를 조금 낮춰볼까요".
  • 핵심 품질은 설명용이성이다. 사용자는 앱이 어떤 심박과 경계를 사용해 판정했는지 확인할 수 있어야 한다.
  • 문장이 자연스러운 것보다 먼저 지켜야 할 조건이 있다. 설명에 나온 사실이 실제 판단에 사용한 사실과 같아야 한다.

2.문제점

  • 생리적인 정답을 알기 어렵다. 실제 Zone 2 경계가 맞는지는 실험실 장비 없이 확인하기 어렵다. 대신 설명이 앱 내부의 판단 과정과 일치하는지는 확인할 수 있다.
  • 판단과 설명을 같은 사실에서 만들어야 한다. 설명을 나중에 추측해서 붙이면 실제 판단과 다른 이유가 나올 수 있다.
  • 판단 기준이 계속 바뀐다. 개인 경계는 러닝마다 갱신되고, 설명은 늘 그 최신 값을 보여줘야 한다.
  • 생성된 설명은 확인이 필요하다. LLM은 이미 정해진 사실을 자연스럽게 표현하는 역할만 맡고, 문장에 나온 숫자와 방향은 규칙이 다시 확인한다.

많은 사람의 데이터로 미리 학습한 모델이 판정과 코칭을 직접 내놓는다. 판단 과정은 수많은 내부 숫자에 흩어져 있어 사람이 읽을 수 없다. 그래서 설명은 결정이 난 뒤에 별도 분석 도구나 LLM이 추정해서 만들어 붙인다.

DP1. 설계결정 및 근거

3

1.최종 채택 구조

후보 1: 규칙/통계 기반 개인화 아키텍처 채택

2.채택 근거

  • 판정과 설명이 같은 사실을 사용한다. "심박 145가 상한 132를 넘었다"처럼 판정에 사용한 숫자와 규칙이 설명의 재료가 된다. 코칭 문장마다 근거와 생성 경로를 기록해 리포트에서 다시 확인할 수 있다.
  • 사용자의 정정이 바로 반영된다(제어가능성). 러닝 중 "그건 내 느낌과 달라"라고 답하면(말하기 테스트) 그 자리에서 개인 경계가 움직이고, 얼마나 움직였는지 화면에 보인다. 2안은 이런 정정을 모아 모델을 다시 학습해야 반영되고, 제대로 반영됐는지 확인하기도 어렵다.
  • 이 과제의 조건에 맞는다. 2안은 충분한 학습 데이터와 정답이 있을 때 장점을 확인할 수 있다. 이 과제에는 두 가지가 모두 없으므로, 동작을 직접 확인할 수 있는 1안이 더 적합하다.
  • 설명 근거를 따로 추정하지 않는다. 설명에 필요한 숫자와 판정 이유는 이미 계산된 값에서 가져온다. LLM 문장 생성은 별도로 실행해 실시간 판정을 막지 않는다.

3.보완 계획

  • 이번 과제에서 확인: 선언한 문장 집합에서 미등록 숫자 차단율 100%(5/5), 사실 문장 통과율 100%(3/3), 근거 기록 저장·복원 시험 통과.
  • 향후 확인: 실제 사용자가 설명을 쉽게 이해하는지는 향후 사용자 평가로 확인한다.

Appendix. DP1 상세 설계 내역

A

1.이 설계 결정이 다루는 품질 문제

  • 판단과 설명이 서로 다른 값에서 만들어지면 근거를 믿기 어렵다 → 설명용이성
  • 개인 경계가 바뀌면 설명도 최신 경계를 사용해야 한다 → 기능적응성
  • 설명 문장의 숫자와 방향을 시스템이 확인할 수 있어야 한다 → 제어가능성
  • 판정과 근거 값의 연결을 같은 입력으로 반복 확인할 수 있어야 한다 → 테스트가능성

2.채택안 상세 설계 — 추상 블록을 하위 모듈(실제 클래스)까지 전개

단계하는 일
1. 사실 확정규칙/통계가 판정과 근거 숫자를 확정한다 — 설명의 재료는 전부 여기서 나온다
2. 근거 기록각 수치의 출처(관측/학습/설계)와 코칭의 근거 관측이 그 자리에서 기록된다
3. 표현 한정LLM은 확정된 사실을 문장으로 바꾸는 일만 한다 — 이유를 지어내지 않는다
4. 표현 검사나가는 문장의 형식, 방향, 숫자를 규칙이 다시 검사한다
5. 추적 열람리포트에서 문장을 누르면 근거 관측과 생성 과정을 그대로 볼 수 있다
