DP2. 제어가능성 — LLM의 권한을 제한하는 구조

생성 문장이 판정과 어긋나거나 LLM을 사용할 수 없을 때 코칭을 통제하는 두 가지 설계안을 비교한다.

DP2. 설계 문제 정의

3

1.배경

  • 이 앱은 코칭 문장을 만들 때 폰 안에서 실행되는 LLM을 사용한다.
  • LLM의 출력은 항상 같지 않다. 판정은 "속도를 낮추기"인데 생성 문장은 반대로 "속도를 올리기"라고 말할 수 있다.
  • 그런데 코칭은 달리는 중에 실시간 음성으로 나간다. 사람이 문장 하나하나를 검사해 줄 수 없다. 통제는 사람 손이 아니라 자동으로 작동하는 구조여야 한다. 그 구조를 고르는 것이 이 설계 결정이다.

2.문제점

  • 프롬프트만으로는 어긋난 문장을 막지 못한다. 판정은 "초과 — 늦춰라"인데 문장은 "속도를 올려요"가 나올 수 있다. 다만 정답 방향은 LLM 밖의 규칙이 이미 정해 두었다 — 잘못 만들어지는 것은 못 막아도, 나온 문장을 정답과 대조해 잘못 나가는 것은 막을 수 있어야 한다.
  • LLM이 없는 상황도 있다. 지원하지 않는 기종이 있고, 첫 모델 다운로드가 끝나기 전이거나 응답이 늦거나 실패할 수도 있다. 어느 경우든 코칭은 끊기면 안 된다.
  • 정해 둔 고심박 규칙은 먼저 동작해야 한다. 설정된 임계값을 넘으면 LLM을 기다리지 않고 규칙 문구를 사용한다.
  • 통제가 작동했는지 나중에 확인할 수 있어야 한다. 어떤 문장을 왜 기각했는지 기록으로 남고, 사용자도 말하기 테스트로 판정 기준을 정정하고 설정에서 코칭 빈도와 말투를 바꿀 수 있어야 한다.

규칙이 방향과 사실 숫자를 확정하면 LLM은 그 재료로 문장만 만든다. 나온 문장은 형식, 방향, 숫자 세 가지 검사를 거치고, 걸리거나 LLM이 실패하면 "속도 줄이기" 같은 짧은 문구로 바꿔 내보낸다. 위험 심박 권고는 LLM을 거치지 않고, 모든 호출의 경로와 기각 사유가 기록된다

심박과 페이스를 프롬프트로 주고 LLM이 코칭 방향과 문장을 함께 정한다. 프롬프트 지시와 간단한 출력 필터로 잘못된 문장을 줄인다.

DP2. 설계결정 및 근거

3

1.최종 채택 구조

후보 1: 규칙 확정 + LLM 표현 한정 아키텍처 채택

2.채택 근거

  • 문제가 생기면 손쓸 수단이 구조 안에 있다. 어긋난 문장은 기각되고(교정), LLM이 없으면 짧은 문구로 대신하고(보완), 위험 심박이면 LLM을 거치지 않는다(안전전환). 셋 다 사람 손 없이 자동으로 작동한다. 2안에서 손쓸 수단은 프롬프트 수정뿐이고 그 효과는 보장되지 않는다.
  • LLM의 성능과 관계없이 통제가 동작한다. 출력을 규칙이 다시 검사하고, 기준에 맞지 않으면 기본 문구로 바꾼다. 2안은 LLM이 프롬프트를 잘 따르는지에 더 크게 의존한다.
  • 실패해도 코칭이 이어진다. LLM이 없거나 실패했을 때 1안의 최악은 "짧은 문구 코칭"이고, 2안의 최악은 "코칭 중단"이다.
  • 통제 작동을 데이터로 확인한다. 어떤 문장이 왜 기각됐고 언제 폴백했는지가 세션마다 기록되어 리포트에서 확인할 수 있다.
  • DP1과 같은 구조에서 나온다. 판단을 규칙에 두었기 때문에 설명이 실제 판단과 일치하고(DP1), 나온 문장을 검사할 정답도 시스템 안에 생긴다(DP2). 하나의 구조 선택이 두 품질을 함께 만든다.

3.보완 계획

  • 이번 과제에서 확인: 선언한 검증 집합에서 위반 문장 10/10 차단, 정상 문장 5/5 통과, LLM 실패·로딩·모델 없음 경로 시험 통과.
  • 향후 확인: 더 다양한 한국어 표현으로 시험 집합을 늘리고, 자주 차단되는 표현을 바탕으로 프롬프트와 검사 규칙을 다듬는다.

Appendix. DP2 상세 설계 내역

A

A1.문제점이 걸리는 품질 속성

  • 작은 LLM은 프롬프트를 가끔 어긴다 → 제어가능성
  • 실시간이라 출력마다 사람이 검수할 수 없다 → 제어가능성
  • 미지원 기종, 다운로드 전, 지연, 오류로 LLM이 없을 수 있다 → 강건성
  • 위험 심박 권고는 지연과 오작동을 허용할 수 없다 → 제어가능성(안전전환)
  • 통제가 작동했는지 사후 확인이 필요하다 → 제어가능성(감사)
  • 사용자도 개입할 수 있어야 한다 → 제어가능성(교정, 보완)
  • 통제가 과하면 표현이 굳는다 → 기능적응성

A2.채택안의 통제 단계 (판단 권한 제한부터 기록까지 순서대로 적용)

층하는 일제어 유형
1. 격리판단은 규칙, LLM은 문장만 — 맡기는 권한 자체를 좁힌다예방
2. 출력 검사형식(길이), 방향(판정과 모순이면 기각), 숫자(관측에 없는 숫자면 기각)교정
3. 기본 문구검사에 걸리거나 LLM이 실패하면 "속도 줄이기" 같은 짧은 문구로 바꿔 내보낸다보완
4. 안전 분리위험 심박 권고는 LLM을 거치지 않는다안전전환
5. 사람 개입 + 기록말하기 테스트로 판정 기준 정정, 설정 토글, 모든 호출 경로와 기각 사유를 세션에 기록교정, 보완, 감사

평가 조건: 폰 안에서 실행하고, 실시간으로 문장을 내보내며, LLM을 사용할 수 없는 상황에도 코칭이 이어져야 한다는 조건에서 비교했다. 사람이 모든 출력을 미리 검토할 수 있는 서비스라면 2안의 평가가 달라질 수 있다.

A4.예상 질문

  • "프롬프트를 잘 쓰면 2안도 통제되지 않나?" → 프롬프트 규정은 권고이지 강제가 아니다. 물론 2안에도 규칙 판정기를 병렬 검증기로 붙일 수는 있다 — 그러나 그 검증기가 곧 규칙 판정이고, 불일치 때 규칙을 따라야 하는 순간 1안 구조로 수렴한다. 2안 고유의 것은 "규칙 없이 LLM만 믿는 구간"인데, 그 구간이 통제되지 않는다.
  • "검사가 정상 문장까지 기각해 코칭이 굳지 않나?" → 가능하다. 그래서 기각이 전부 기록되고, 기각률이 높으면 기준을 데이터로 조정한다. 기각의 비용은 덜 자연스러운 짧은 문구이지 코칭 중단이 아니다.

A5.용어 대조(심사용)와 근거 문헌

개입 가능성 = intervenability(ISO/IEC 25059 제어가능성의 핵심) / 맡기는 일 자체를 좁히는 통제 = architectural containment(구조적 격리) / 실패 시 무손상 전환 = fail-safe fallback / 사람 개입 = HITL(루프 안 교정), HOTL(루프 위 감독) / 사후 확인 = audit(감사)

근거 문헌: ISO/IEC 25059(제어가능성 정의) / LLM 가드레일 계층 방어 서베이(구조적 격리가 가장 강한 층) / LLM 단독 판단 회피 권고 / 소형 모델 지시 이행 한계(이행률 60% 미만 사례)
