부록 — 심박 관련 ML 검토와 아키텍처 상세

설계 과정에서 검토한 심박 관련 ML 대안과 시스템의 사용 사례·실행·모듈·배포 구조를 정리한다.

부록. 심박 관련 ML 대안 검토 기록

A

이 부록은 심박과 운동 상태를 추론하는 ML의 시험 구현과 검토 결과를 정리한다. 코칭 문장을 표현하는 LLM과 그 통제 구조는 DP3에서 별도로 다룬다.

1.검토한 대안과 최종 반영

검토 대상확인한 내용최종 구조에 반영한 방향
Zone 판정 MLP가상 조건에서는 학습과 평가가 가능했지만, 실제 사용자의 Zone 판정을 비교할 기준값이 부족했다. 말하기 응답으로 조정한 개인 경계와 별도의 판정 기준을 갖게 되는 문제도 있었다.현재 심박과 개인 경계를 직접 비교해 Zone을 판정한다.
개인 경계 추정 MLP개인별 유산소 역치를 학습할 실제 기준 데이터가 부족해 모델 출력의 정확도를 확인하기 어려웠다.프로필로 첫 경계를 정하고 말하기 응답으로 개인 경계를 조정한다.
이후 심박 예측 NN가상 심박 변화는 학습할 수 있었지만, 실제 사용자의 이후 심박을 얼마나 정확하게 예측하는지는 확인하기 어려웠다.예측값 대신 실제로 관측한 심박 변화와 세션 지표를 분석한다.
규칙 오차 보정 NN규칙이 놓친 오차를 작은 모델로 보정하는 방안을 검토했지만, 실제 데이터에서 효과를 판단할 근거가 부족했다.현재 판정에는 적용하지 않고 실제 비교 데이터가 확보되면 다시 검토한다.

2.기록의 해석 범위

시험 구현 결과는 각 모델의 학습 가능성과 현재 데이터의 한계를 확인한 개발 기록이다. 최종 선택은 이 결과 하나가 아니라 DP1과 DP2에서 비교한 기능적응성·설명용이성·테스트가능성, 운영 제약과 Tradeoff를 함께 고려했다.

가상 조건의 결과는 구조와 학습 가능성을 살펴본 자료이며 실제 사용자의 생리학적 정확도를 뜻하지 않는다.

부록. 사용 사례(Use Case)

A
  • 그림의 사용자는 러너와 개발·검증 담당자다. 러너는 앱의 러닝 기능을 사용하고, 개발·검증 담당자는 시험 입력으로 다섯 QAS를 반복 검증한다. 검증용 기능은 개발·검증 환경에서만 사용하며 일반 사용자에게 제공하지 않는다.
  • 러너의 흐름은 프로필 등록 → 세션 시작 → 존 확인과 음성 코칭 → 말하기 테스트 응답 → 리포트와 코칭 근거 확인 순서다. 말하기 테스트 응답은 개인 경계 갱신에 사용된다.
  • 설정에서 코칭 빈도·음성·말투 등을 변경할 수 있다. 홈과 설정 화면에서는 Gemini Nano 모델의 상태와 다운로드 필요 여부를 확인할 수 있다.

부록. 시스템 관계도(Context View)

A
  • Zone2Runner는 폰 앱과 워치 앱으로 구성된다. 워치는 심박과 케이던스를 측정해 폰으로 보내고 화면에 러닝 정보를 표시한다. 폰은 판정·분석·개인화·코칭을 담당한다.
  • 외부 시스템은 Health Services, 폰 GPS, 기기의 별도 프로세스에서 실행되는 Gemini Nano/AICore, Open-Meteo와 OSM 지도 타일 서버다. 날씨를 조회할 때는 반올림한 위도와 경도를 Open-Meteo로 전송하고, 지도 화면에서는 OSM 타일을 요청한다. 심박·개인화·세션 분석 데이터는 자체 서버나 외부 AI API로 보내지 않는다.
  • LLM에는 규칙이 확정한 값과 문장 작성 지시만 전달한다. 생성 결과가 방향·숫자·형식 검사를 통과하지 못하면 차단하고 기본 문구로 전환한다. 리포트에는 판정값과 문장 생성 경로를 함께 기록한다.

부록. 모듈 구조(Module View)

A
  • 이 그림은 파일 목록이 아니라 모듈 사이의 의존 방향을 보여 준다. 공통 데이터 모델은 Android 플랫폼 기능에 의존하지 않으며, 판정·개인화·분석의 핵심 계산도 기기 기능과 분리돼 있다.
  • 이러한 분리 덕분에 기기 없이 단위시험 170개를 실행할 수 있다. 이 숫자는 제품의 정확도가 아니라 코드 변경 후 자동으로 다시 확인할 수 있는 범위를 뜻한다.
  • 실제 센서와 시험 입력은 같은 RunSource 인터페이스를 사용한다. 따라서 입력 이후의 판정 흐름을 바꾸지 않고 같은 시험 시나리오를 반복할 수 있다.

부록. 실행 구조(C&C View)

A
  • 실행 흐름은 센서 입력 → 입력 검사 → 규칙 판정·개인 경계·분석·LLM 표현 → 출력 검사 → 화면·음성·리포트 순서다. 세션 결과와 개인 경계는 폰에 저장된다.
  • DP1~DP3의 그림은 같은 아키텍처에서 기능적응성·설명용이성·제어가능성과 관련된 경로를 각각 강조한다. 강건성과 테스트가능성은 전체 실행 흐름을 지원하는 공통 설계로 반영했다.

A

부록. 배포 구조(Deployment View)

A
  • 시스템은 워치, 폰, 기기의 AICore 프로세스와 외부 Open-Meteo·OSM 타일 서버에 배포된다. 세션과 개인화 값은 폰에 저장한다.
  • 워치에서 측정한 심박과 사용자 응답은 Wearable Data Layer를 통해 폰으로 전달된다. 폰은 확정한 화면용 Zone을 /run/live 경로로 매초 워치에 전송한다. 따라서 Zone 판정을 폰에서만 수행한다는 원칙이 배포 구조에서도 유지된다.
  • Gemini Nano는 AICore라는 별도 프로세스에서 실행되므로 앱에서 AICore 프로세스의 CPU와 메모리를 직접 측정할 수 없다. 보고서에는 앱에서 측정할 수 있는 호출 시간과 처리 경로, 앱 메모리만 기록한다.
