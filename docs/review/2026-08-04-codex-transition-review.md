## 1. 이번 검토의 결론

Zone2Runner에는 인증 보고서의 재료가 이미 충분하다. 특히 다음 설계 논지는 강하다.

> 개인 Zone 2의 실험실 참값과 대량 학습 데이터가 없는 조건에서, 판정은 투명한 규칙/통계에 두고, 개인 경계는 사용자 라벨로 적응시키며, 제한된 온디바이스 LLM에는 표현만 맡긴다. 입력/출력 가드레일과 폴백으로 실패를 통제하고, 센서 소스 추상화와 시뮬레이션으로 같은 자극을 재현한다.

다만 현재 산출물은 좋은 재료를 모두 본문에 같은 비중으로 올려 **핵심 설계 논지가 묻히는 상태**다. 보고서 46장, DP 5건, QA 6건을 모두 강조하면서 "무엇이 가장 중요한 설계 결정인가"가 흐려졌다. 문장 단위 교정보다 먼저 보고서의 논리 계층을 다시 세워야 한다.

## 2. 확인한 자료와 현재 상태

### 인증 샘플에서 확인한 형식

샘플 PDF는 표지 포함 31개 내용 페이지로 구성된다.

1. 과제 소개: 배경/필요성, 개요
2. 요구사항: 기능/제약, QAW와 Utility Tree 기반 QA 선정
3. 설계: DP별 `문제 정의 -> 2개 대안 비교 -> 결정/근거`, 최종 아키텍처
4. 구현/검증: QA 요약 표, 구현 화면
5. 결론
6. Appendix: 지표 근거, Use Case, Context/Module/C&C/Deployment View, QA 상세 결과

샘플은 내용의 사실성보다 **구성과 흐름을 참고하라는 예시**다. 따라서 샘플의 임의 수치나 피상적인 대안 비교를 따라 하기보다, 형식만 따르고 Zone2Runner의 실제 근거를 넣어야 한다.

### 저장소의 문서 구조

| 위치 | 현재 역할 | 판단 |
|---|---|---|
| `framework/` | 강의 프레임워크와 과제 샘플 | 변경하지 않는 입력 자료 |
| `spec/` | FR/제약/QA와 기능 명세 | 요구사항 정본 |
| `arch/` | 전체 아키텍처, ADR, DP, 도식 | 설계 정본 |
| `report/` | 인증 보고서 파트별 Markdown 원고 | 보고서 내용 정본으로 유지 |
| `docs/src/` | 화면용 HTML 원고 | `report/`의 표현물로 취급 |
| `docs/` | 빌드된 HTML 덱 | 배포 산출물 |
| `HANDOFF.md` | Claude 작업 이력 | 144KB로 비대함. 최신 판단의 정본으로 사용하지 않음 |
| `.claude/skills/` | ADR/Spec/Report 작성 규칙 | 템플릿 일부는 유효하나 논리/검증 규칙은 부족 |

현재 `report/`와 `docs/src/` 모두 원고처럼 편집되고 있어 드리프트 위험이 있다. 향후에는 내용을 `report/`에서 먼저 확정하고, `docs/src/`는 렌더링용으로만 동기화한다.

### 구현에서 확인한 핵심 근거

- 폰 앱: 판정/분석/개인화/코칭/리포트의 주체
- 워치 앱: 심박/위치/케이던스 수집과 표시, 폰과 메시지 교환
- 규칙 판정과 방어: `RunEngine`, `ZoneJudge`, `OutlierGuard`, `SafetyGuard`, 표시 존 히스테리시스
- 개인화: `Personalization`과 말하기 테스트 기반 경계 갱신
- 관측 분석: 드리프트, HRR, GAP, 케이던스 안정성 등의 독립 분석 모듈
- LLM 경계: `LlmCoach`, `DirectionGuard`, `NumberGuard`, 규칙 폴백, 호출 근거 기록
- 검증 구조: `RunSource` 인터페이스, 가상/수동 러너 소스, 순수 JVM 테스트
- 테스트 소스: 29개 파일, `@Test` 선언 153개, QA 측정 테스트 7개

**2026-08-04 재검증 완료**: Android SDK와 Build Tools 34.0.0은 `D:\Android\Sdk`에 정상 설치되어 있었다. 초기 실패는 설치 누락이 아니라 실행 환경의 SDK 경로 인식 문제였다. `ANDROID_HOME`과 `ANDROID_SDK_ROOT`를 모두 지정하고 캐시를 무시해 재실행한 결과, **29개 테스트 스위트의 153개 테스트가 실패/오류/건너뜀 없이 모두 통과**했다. QA 측정 파일 7개도 `app/app/build/qa-measurements/`에 다시 생성됐다.

```powershell
cd D:\Github\zone2runner\app

```

## 3. 잘된 점

1. **제약이 설계를 실제로 만들었다.** 비용 0, 대량 데이터 없음, 개인 참값 없음이 규칙/베이지안/온디바이스/시뮬 구조로 이어진다.
2. **LLM의 권한을 제한했다.** 판단과 안전을 모델에 위임하지 않고 표현만 맡긴 선택은 AI S/W 설계 역량을 보여주기 좋다.
3. **실패 경로가 설계되어 있다.** 모델 미가용, 출력 모순, 숫자 생성, 센서 이상치, 신호 두절을 가드/폴백/감사로 다룬다.
4. **설계-구현 추적성이 높다.** DP와 ADR의 개념이 실제 클래스와 테스트로 이어진다.
5. **검증의 한계를 스스로 인식한다.** 시뮬 결과를 실인간 정확도로 일반화하지 않는다는 원칙이 이미 문서에 있다.

## 4. 우선 해결할 논리 문제

### P0. 보고서의 중심 질문이 앞에 고정되어 있지 않다

현재 문서에는 "설명용이성", "기능적응성", "참값 없음", "약한 LLM"이 반복되지만 하나의 질문으로 먼저 묶이지 않는다. 다음 문장을 전 보고서의 기준 질문으로 사용한다.

> 실험실 참값이 없는 개인 운동 강도 문제에서, 제한된 온디바이스 모델을 사용하면서도 근거를 설명하고, 사용자가 교정하고, 실패를 통제하며, 반복 검증할 수 있는 AI 코칭 시스템을 어떻게 설계할 것인가?

모든 FR, QA, DP, 구현, 측정은 이 질문에 답해야 한다.

### P0. 모든 QA를 ASR로 올려 우선순위가 사라졌다

현재 QA 6개의 중요도가 모두 7 이상이라 전부 ASR이다. 이는 QAW/Utility Tree를 했지만 실제 선택은 하지 않은 인상을 준다.

- 헤드라인 ASR: 설명용이성, 기능적응성, 제어가능성
- 필수 지원 QA: 강건성, 테스트가능성
- 예산/통과 조건: 수행효율성

최종 중요도와 난이도는 숫자를 다시 매기는 것보다, 이해관계자/자극/실패 영향/아키텍처 파급을 근거로 설명한다. 모든 QA가 중요하더라도 본문 우선순위는 분명히 둔다.

### P0. DP 5건이 같은 무게라 핵심 결정이 묻힌다

현재 통합 덱은 46장으로 샘플보다 약 15장 길다. DP1과 DP2는 같은 구조 선택(규칙이 판단, LLM은 표현)을 다른 QA 관점에서 반복한다. DP4/DP5는 중요한 지원 결정이지만 인증 본문의 중심 설계 결정과 같은 분량을 쓸 필요는 없다.

권장 본문 DP는 다음 3개다.

1. **판단과 생성의 권한 분리**: 투명한 규칙/통계 판단 + LLM 표현 한정. 설명용이성과 제어가능성을 함께 다룬다. 현재 DP1+DP2 통합.
2. **공식 초기값에서 사용자 라벨로 적응**: 온라인 베이지안 개인화. 현재 DP3.
3. **참값 없는 시스템의 검증 가능 구조**: 센서 소스 추상화 + 재현 시뮬레이션 + 실제 기기 검증의 역할 분담. 현재 DP5 중심, DP4의 노이즈 주입을 연결.

현재 DP4의 계층 방어는 최종 아키텍처와 QA 검증 본문에 넣고 상세 대안 비교는 Appendix로 보낸다. 기존 DP 문서는 삭제하지 않고 설계 정본/부록 근거로 보존한다.

### P0. 정량 검증의 의미가 일부 과장되어 보일 수 있다

- QA1의 5개 숫자 기각 테스트는 "설명용이성 달성" 전체가 아니라 **숫자 무결성 가드의 지정 케이스 통과**다. 사용자 이해도와 설명 충실도 전체를 대변하지 않는다.
- QA2의 시뮬 수렴은 **베이지안 갱신 메커니즘과 클램프의 동작**을 검증한다. 실제 사람의 역치 추정 정확도를 검증하지 않는다.
- "오답 라벨 10%에서 최종 0.09bpm"은 정상 사례보다 좋아 보여 직관을 거스른다. 시드/분포/반복 통계 없이 대표값만 싣지 않는다.
- QA4의 범위 밖 값 100% 기각은 범위 검사 코드의 구조적 결과다. 강건성의 핵심 증거는 번복 억제와 실제 변화 반응의 균형이다.
- QA5의 테스트 개수는 보조 정보다. 핵심은 같은 자극의 재현, 관찰 가능성, 요구사항-테스트 추적성이다.
- QA6의 0.07ms는 JVM 환경 로직 측정이다. 모바일 단말의 화면/워치 통신/LLM/TTS 성능으로 확장해서 표현하지 않는다.

검증 표는 각 결과에 `검증 대상`, `환경`, `표본`, `말할 수 있는 것`, `말할 수 없는 것`을 붙인다.

### P0. "데이터가 기기를 떠나지 않는다"는 현재 구현과 충돌한다

LLM과 주요 추론은 온디바이스지만 앱은 다음 네트워크 기능을 사용한다.

- Open-Meteo 호출에 위도/경도를 소수점 네 자리까지 전송한다.
- osmdroid 지도 타일 요청은 위치가 포함된 타일 영역을 외부 서버에 드러낼 수 있다.
- 앱 Manifest에 인터넷 권한이 있다.

따라서 "러닝/개인 데이터 비이탈" 또는 "모든 데이터가 기기를 떠나지 않는다"는 표현은 쓰지 않는다. 다음처럼 범위를 한정한다.

> 심박, 프로필, 개인화 파라미터, 세션 분석은 자체 서버나 외부 AI API에 업로드하지 않고 기기에서 처리한다. 다만 날씨와 지도 기능은 외부 서비스에 위치 기반 요청을 보낸다.

프라이버시를 성과로 강조하려면 위치 요청의 선택권/고지/비활성 경로가 구현되어 있는지 별도 확인해야 한다.

### P1. "AI" 범위가 넓고 방어 논리가 분산되어 있다

FR2~FR6을 모두 AI 관련으로 표시하면 단순 규칙과 통계까지 AI라고 부풀린 인상을 줄 수 있다. 개별 알고리즘의 명칭보다 **AI 시스템 경계**를 먼저 정의한다.

- AI 기반 요소: 온디바이스 LLM 표현/요약, 온라인 베이지안 개인 적응
- AI를 통제/지원하는 S/W 요소: 규칙 판정, 분석, 입출력 가드레일, 프로비넌스, 시뮬 검증

즉 "모든 기능이 AI"가 아니라 "AI 구성요소를 신뢰 가능하게 운영하는 전체 S/W 아키텍처"가 과제 대상이다.

### P1. 대안 비교의 공정성과 별점 근거가 약하다

별점이 DP마다 반복되고, 같은 QA의 의미가 표마다 달라 별도 해명 문단이 필요하다. 별점 수를 줄이고 다음 네 축을 공통으로 사용한다.

- 제약 충족 여부
- 핵심 QA 효과
- 실패 모드와 통제 가능성
- 구현/운영 비용

대안은 "일부러 나쁜 안"이 아니라 조건이 달라지면 채택될 수 있는 실제 대안으로 설명한다. 점수보다 탈락 조건과 Trade-off 문장이 중요하다.

### P1. 문장과 용어가 반복되어 발표 호흡이 무겁다

"참값 없음", "정체성", "구조", "검증"이 여러 파트에서 같은 설명으로 반복된다. 정의는 앞에서 한 번 하고 이후에는 결과만 연결한다. 문장 교정 시 다음을 적용한다.

- 한 문장에는 주장 하나만 둔다.
- 구호형 표현은 장 제목/결론에만 사용한다.
- 괄호 속 영문은 최초 정의와 Appendix에 한정한다.
- "~할 수 있다"보다 실제 구현/측정 상태를 쓴다.
- "완벽", "보장", "전부 갖췄다"는 기계적으로 증명되는 좁은 범위 외에는 피한다.

### P2. 문서 운영 비용이 크다

- `HANDOFF.md`는 일지와 현재 상태가 섞여 144KB다.
- `report/`와 `docs/src/`가 중복 원고다.
- 일부 명세는 문서 상단의 정합 note만 최신이고 본문에는 폐기된 내용이 남아 있다.

이번에 만든 `AGENTS.md`를 짧은 지속 규칙으로 사용한다. 이후 `HANDOFF.md`는 최신 상태 요약과 역사 로그를 분리하고, HTML은 Markdown 원고가 확정된 뒤 한 방향으로만 동기화한다.

| DP3 검증 구조 | 3 | 시뮬과 실기기의 역할 분담 |
| 최종 아키텍처 | 2~3 | 세 DP가 하나의 시스템으로 조립됨 |
| 구현 | 3~4 | 화면 나열이 아니라 설계 결정의 사용자 접점 |
| 품질 검증 | 3~4 | 결과, 증거 수준, 남은 실기기 항목 |
| 결론 | 1 | AI S/W 설계 역량과 한계 |

Appendix에는 전체 FR/QA 표, 강건성 DP, 상세 아키텍처 뷰, 측정 방법/원자료, 클래스 추적표, 미완료 실기기 검증을 둔다.

## 6. 발표 대본 원칙

대본은 보고서 문장을 읽는 문서가 아니라 **슬라이드 사이의 인과를 설명하는 별도 산출물**로 만든다.

- 먼저 10~12분 전체 대본을 만든 뒤, 5분 요약본과 예상 질문 답변을 파생한다.
- 각 슬라이드는 `핵심 한 문장 -> 그림 읽는 순서 -> 다음 슬라이드 연결`로 쓴다.
- 수치는 의미와 한계를 함께 읽는다. 예: "1.73bpm 정확도"가 아니라 "가상 라벨 조건에서 갱신식이 수렴했다".
- 구현 클래스 이름은 질문 대응용 부록에 두고, 본 발표에서는 책임과 데이터 흐름으로 설명한다.
- 예상 질문은 `왜 AI인가`, `정확도는 어떻게 검증했나`, `LLM이 꼭 필요한가`, `시뮬은 자기 채점 아닌가`, `의료 안전은 어떤가`, `데이터가 정말 외부로 안 나가나`를 반드시 포함한다.

## 7. 단계별 실행 계획과 완료 기준

### 1단계. 주장-근거 대장 확정

- 보고서의 핵심 주장마다 구현 파일, 테스트, 측정 환경, 한계를 연결한다.
- 완료 기준: 근거 없는 수치/효과 주장 0건, `완료/부분 완료/계획` 구분 완료.

### 2단계. 요구사항과 QA 논리 정리

- 중심 질문, AI 시스템 경계, QA 우선순위, ASR 선정 근거를 다시 쓴다.
- 완료 기준: 각 핵심 ASR이 하나 이상의 DP와 검증 항목으로 왕복 추적됨.

### 3단계. DP 본문 3건으로 재편

- 현재 DP1+DP2를 통합하고 DP3/DP5를 핵심화한다.
- DP4는 지원 설계/부록으로 재배치하되 기존 정본은 보존한다.
- 완료 기준: 각 DP가 동일한 비교 틀을 사용하고, 대안/Trade-off/결정/한계가 한 번씩만 등장.

### 4단계. 검증 재현성과 표현 교정

- 전체 테스트와 QA 측정의 재실행은 2026-08-04 완료했다(153/153 통과, QA 측정 파일 7개 재생성).
- 다음 작업에서는 각 QA 측정 파일의 값이 보고서 표와 일치하는지 대조하고 실행 환경/날짜를 보고서 증빙에 반영한다.
- 완료 기준: 보고서의 모든 수치가 저장된 산출물에서 재현되거나 "과거 기록/미재현"으로 표기됨.

### 5단계. 보고서 원고 재작성

- `report/`에서 본문 28~32장 기준으로 원고를 통합한다.
- 한국어 문장, 표 제목, 그림 캡션, 장 사이 연결 문장을 교정한다.
- 완료 기준: 한 슬라이드 한 메시지, 본문 중복 제거, 샘플의 큰 흐름과 일치.

### 6단계. HTML/PDF 시각 검증

- 확정 원고를 `docs/src/`에 반영하고 HTML을 빌드한다.
- PDF로 출력해 잘림, 표 밀도, 글자 크기, 그림 가독성을 페이지별 확인한다.
- 완료 기준: 레이아웃 결함 0건, 본문과 Appendix 구분 명확.

### 7단계. 발표 대본과 질문 대응 자료 작성

- 전체 대본, 요약 대본, 슬라이드별 발표 노트, 예상 질문 답변을 작성한다.
- 완료 기준: 실제 낭독 시간 확인, 슬라이드 번호와 대본 1:1 대응, 모든 수치의 한계 발화 포함.
