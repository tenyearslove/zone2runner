# 사용자 피드백 검토 — HTML p.3~14

- 날짜: 2026-08-04
- 상태: 논의 중
- 원칙: 피드백을 그대로 반영하지 않고 사실, 과제 목적, 전체 일관성과 대조해 `동의`, `부분 동의`, `다른 제안`으로 평가한다.
- 적용 범위: 지표와 QAS 구성이 합의되기 전에는 HTML 본문을 일괄 수정하지 않는다.

## 1. 먼저 합의할 제안

### 1.1 품질 속성 구성

현재 네 AI 품질은 유지하고, 일반 소프트웨어 품질인 **테스트가능성**을 QA5로 복원하는 것을 권한다.

| ID | 품질 속성 | 제안 | 이유 |
|---|---|---|---|
| QA1 | 설명용이성 | 유지 | 판정에 사용한 사실과 설명을 연결하는 구조를 만들었다. |
| QA2 | 기능적응성 | 유지 | 말하기 테스트 응답으로 개인 경계를 갱신하는 핵심 기능이다. |
| QA3 | 제어가능성 | 유지하되 표현 완화 | LLM의 역방향 발화를 흔한 현상처럼 말하지 않고, 출력 검사·미가용 폴백·권한 제한에 초점을 둔다. |
| QA4 | 강건성 | 유지 | 센서 이상치와 경계 부근의 흔들림을 방어하는 구조를 만들었다. |
| QA5 | 테스트가능성 | 정식 QAS로 복원 | 실제 달리기를 반복하기 어려운 제약이 RunSource 추상화, 고정 시드, 가상 러너라는 아키텍처 결정을 만들었다. |
| 수행효율성 | 보조 제약 유지 | 정식 QAS로 복원하지 않음 | JVM 로직 시간만으로 워치·화면·LLM을 포함한 기기 성능을 주장할 수 없다. |

과제 규정은 품질 속성 4개 이상, 그중 AI 품질 2개 이상이다. 위 구성은 AI 품질 4개와 일반 품질 1개로 규정을 만족하면서, 시뮬레이션에 들인 설계 노력을 더 잘 보여 준다.

### 1.2 QAS 지표 표현 초안

백분율만 쓰면 표본 수가 감춰지고, 건수만 쓰면 지표처럼 보이지 않는다. 따라서 **비율과 건수를 함께 쓰는 방식**을 권한다.

| QA | 권장 표기 | 해석 제한 |
|---|---|---|
| QA1 설명용이성 | 선언한 문장 집합에서 미등록 숫자 차단율 **100%(5/5)**, 사실 문장 통과율 **100%(3/3)**, 근거 기록 저장·복원 시험 통과 | 작은 회귀시험 집합의 결과이며 모든 한국어 문장의 품질을 뜻하지 않는다. |
| QA2 기능적응성 | 참임계 5종×시드 3종의 **15/15 사례**가 3개 모의 세션 이내 목표 오차에 진입하고, 8세션 뒤 최종 오차 3bpm 이하. 기준 사례에서는 마지막 4세션 폭 4bpm 이하, 세션당 이동 10bpm 이하 | 현재 모의 세션은 세션당 말하기 테스트 응답 5회를 넣는다. 안정성과 이동 폭은 15개 전체가 아니라 기준 사례 하나에서 확인했다. 이 조건을 숨기면 안 된다. |
| QA3 제어가능성 | 선언한 공격·오류 문장 집합에서 위반 탐지율 **100%(10/10)**, 정상 문장 통과율 **100%(5/5)**, 선언한 LLM 미가용 경로의 기본 문구 전환 시험 통과 | 실제 LLM이 이런 문장을 자주 만든다는 뜻이 아니라, 의도적으로 넣은 위반 출력을 가드가 막는 회귀시험이다. |
| QA4 강건성 | 범위 밖 입력 차단율 **100%(50/50)**, 정상 입력 오차단율 **0%(0/500)**, 번복 감소 기준 충족률 **100%(5/5 시드, 실제 67.1~74.7%)**, +10bpm 계단 입력은 2틱 이내 전환 | `실제 이동`이 아니라 시험에서 만든 명확한 계단 입력이다. 실제 센서 정확도나 실제 러닝 결과를 뜻하지 않는다. |
| QA5 테스트가능성 | 워치 없이 기존 네 AI QAS의 자동 검증 경로 **4/4 제공**, 동일 시드 재실행 결과 일치율 **100%(복수 시드)**, 센서·가상 러너가 같은 RunSource 계약으로 엔진에 연결됨 | 153개 시험 수는 회귀 범위를 설명하는 보조 정보이지 제품 정확도 지표가 아니다. 복수 시드 재현율의 정확한 분모는 시험을 보완한 뒤 확정한다. |

QA2는 현재 문서와 코드가 다르다. 문서는 5세션 이내를 말하지만 시험은 15개 사례가 3세션 이내인지 검사한다. 또한 15개 사례의 최종 오차·안착 시험과 기준 사례 하나의 안정성·이동 폭 시험을 분리해서 써야 한다.

## 2. 페이지별 피드백 평가

### p.3 배경과 필요성

- **Zone 2와 유산소 역치 설명 추가: 동의.** 별도 한 페이지를 배정하는 편이 낫다. 다만 `Zone 2 = 유산소 역치`로 단정하면 안 된다. 쉬운 설명은 “숨이 조금 차지만 문장으로 대화할 수 있고, 비교적 오래 유지할 수 있는 낮은 강도”로 시작한다. 전문적으로는 첫 번째 젖산·환기역치 바로 아래를 목표로 보는 견해가 많지만 Zone 2의 정의 자체는 체계마다 다르다.
- **말하기 테스트 배경 추가: 동의.** 편안하게 말할 수 있는지 묻는 방법은 장비 없이 운동 강도를 가늠하는 실용적 대안이다. 다만 개인 역치를 직접 측정한 정답으로 표현하지 않고, 사용자 느낌을 개인화에 반영하는 관측 수단이라고 설명한다.
- **LLM이 반대말을 할 수 있다는 표현: 동의, 완화 필요.** 현재 문장은 실제 발생 빈도 근거 없이 최악 사례를 흔한 문제처럼 썼다. “LLM 출력은 매번 같지 않고, 요청한 형식이나 제공한 숫자를 벗어날 수 있다. 따라서 최종 판단은 규칙이 맡고 출력은 확인한다.” 정도가 적절하다.

참고 연구:
- Zone 2 정의에 전문가 합의가 완전하지 않으며, 첫 젖산·환기역치 바로 아래가 권장된다는 견해: https://pubmed.ncbi.nlm.nih.gov/40010355/
- Talk Test가 운동 강도 조절에 사용할 수 있다는 실험: https://pubmed.ncbi.nlm.nih.gov/25536539/
- Talk Test와 개인의 환기역치 대응에는 오차가 클 수 있다는 결과: https://pubmed.ncbi.nlm.nih.gov/32604216/

### p.4 과제 개요

- **폰·워치·서버 문장: 동의.** “시스템은 폰 앱과 워치 앱으로 구성된다. 폰은 판정·분석·개인화·코칭을 맡고, 워치는 심박을 측정해 결과를 보여 준다. 별도의 자체 서버는 운영하지 않는다.”처럼 연결한다.
- **가상 러너의 randomness: 동의, 구현으로 확인.** `RunSimulator`, `VirtualRunner`, `SimRunnerSource`는 seed 기반 난수, Gaussian 노이즈, 센서 누락·스파이크, 지형과 러너 특성 변화를 사용한다. 같은 seed는 같은 결과를 만들어 재현성도 확보한다. “시드로 재현 가능한 난수 기반 가상 러너”가 정확하다.

### p.6 QAS 표

- **건수형 지표 수정: 동의.** 단, 100%만 쓰지 않고 `100%(5/5)`처럼 분모를 함께 둔다.
- **QA2 지표 수정: 강하게 동의.** 네 기준을 한 줄에 붙이면 어떤 사례가 무엇을 통과했는지 알 수 없다. 15개 스윕과 기준 사례 안정성 시험을 분리한다.
- **테스트가능성 복원: 권장.** 위 1.1의 QA5 제안을 적용한다.
- **“QA에서 설계와 검증으로”: 동의.** “QAS가 설계와 검증으로 이어지는 과정” 또는 “QAS–설계–검증 연결”로 바꾼다.

### p.8 DP1 설계안 그림

- **검수 여부: 검수했다.** DP1 도식은 이미 채택안·비교안·상세안이 분리되어 있어 구조를 크게 바꿀 이유가 없었다. PUML 정본과 PNG가 함께 있으며 2026-08-04에 다시 렌더링했다. 변화가 적은 것은 누락이 아니라 기존 구조를 유지한 결과다.
- 다만 최종 HTML 검수 때 글자 크기와 두 안의 차이가 한눈에 들어오는지는 다시 본다.

### p.9 DP1 근거와 지표

- **“사실 생성은 가볍다”: 동의.** 어색하고 의미가 잘못 읽힌다. “판정 근거를 따로 계산하지 않는다” 또는 “설명에 필요한 근거는 이미 계산된 값에서 가져온다”가 낫다.
- **지표 전면 수정: 동의.** p.6과 동일한 표기를 전 페이지에 적용한다.
- **“합격 기준에는 포함하지 않는다”: 동의.** “실제 사용자가 설명을 쉽게 이해하는지는 향후 사용자 평가로 확인한다.”에서 끝낸다.

### p.10 DP1 상세

- **“문제점이 걸리는 품질 속성”: 동의.** 뜻이 불분명하다. “이 설계 결정이 다루는 품질 문제”로 바꾼다.
- **선정하지 않은 품질 속성 6개: 동의.** 대안 비교에서 부수적인 trade-off를 보는 것은 가능하지만, 현재 표는 모두 프로젝트 QAS처럼 보인다. 선정한 품질 중 이 DP가 실제로 영향을 주는 항목만 남기고, 성능 같은 부수 비용은 문장으로 설명한다. 모든 DP에 네 항목을 억지로 반복할 필요도 없다.
- **예상 질문 분리: 동의.** DP1~DP5의 예상 질문을 제출 HTML에서 빼고 별도 `1차 평가자 질문 목록` 문서로 모은다.

### p.11~14 DP2 제어가능성

- **LLM의 반대 방향 발화 반복: 동의, 전면 완화.** 실제 Gemini Nano가 이런 실수를 자주 했다는 측정이 없다. 위반 문장은 가드 시험을 위해 의도적으로 넣은 공격 사례이지 관측된 빈도가 아니다.
- **DP2 유지 여부: 유지 권장.** DP2의 가치는 “LLM이 자주 반대로 말한다”가 아니라 다음 세 가지에 있다.
  1. 규칙이 코칭 방향을 정하고 LLM의 권한을 문장 표현으로 제한한다.
  2. 모델 미지원·다운로드 전·지연·오류에도 기본 문구로 전환한다.
  3. 숫자·형식·방향 검사를 자동 회귀시험으로 확인한다.
- **p.12가 예전 버전처럼 보인다는 지적: 맞다.** 문법은 일부 다듬었지만 기존의 공격적인 LLM 실패 서사를 거의 유지했다. 실질적인 재작성으로 보기 어렵다. 다음 수정에서 문제 정의, 대안 비교, 지표를 함께 다시 쓴다.
- **“문제가 생기면 손쓸 수단이 구조 안에 있다”: 동의.** “LLM 출력이 기준을 벗어나거나 모델을 사용할 수 없을 때 자동으로 대응한다.”처럼 구체적으로 쓴다.
- **p.14의 여섯 품질 속성: 동의.** 선정한 품질 가운데 DP2가 직접 다루는 제어가능성·강건성·설명용이성만 남기는 방안을 권한다. 기능적응성은 이 DP의 핵심 비교 축이 아니므로 뺀다.

## 3. 공통 수정 규칙

지표가 합의되면 다음을 전체 HTML에 적용한다.

1. 결과는 `백분율(통과 수/전체 수)`로 표기한다.
2. 시험에서 만든 입력은 `실제`라고 부르지 않는다.
3. 공격 사례 주입과 실제 모델에서 관측한 실패를 구분한다.
4. 선정하지 않은 품질 속성은 QAS 표와 DP 별점 표에서 제거한다.
5. 예상 질문은 제출 HTML에서 분리한다.
6. `합격`, `정답`, `보장`처럼 과제 작성자가 단정하기 어색한 표현을 줄인다.
7. Zone 2, 말하기 테스트, ASR, 히스테리시스는 쉬운 설명을 먼저 쓰고 전문용어는 괄호로 덧붙인다.
8. 한 번의 교정으로 끝내지 않고 각 파트마다 논리 검토와 한국어 검토를 분리해 반복한다.

## 4. 아직 합의가 필요한 항목

1. 품질 속성을 `AI 품질 4개 + 테스트가능성 1개`의 총 5개로 확정할지
2. QA2의 시간 단위를 `세션`으로 유지할지, `말하기 테스트 응답 횟수`를 함께 표시할지
3. QA5 재현성 지표를 위해 복수 seed 동일 결과 시험을 보완할지
4. DP별 별점 표를 유지할지, 더 단순한 장단점 비교표로 바꿀지
