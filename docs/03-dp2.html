DP2. 설계 문제 정의

3

1.배경

  • 이 앱은 코칭 문장을 만들 때 폰 안에서 도는 작은 LLM을 쓴다. 서버 없이 도는 작은 모델이라 능력에 한계가 있다.
  • 작은 LLM은 시킨 대로 따르는 능력이 불안정하다. 프롬프트에 규칙을 잘 써 두어도 지킨다는 보장이 없다.
  • 그런데 코칭은 달리는 중에 실시간 음성으로 나간다. 사람이 문장 하나하나를 검사해 줄 수 없다. 통제는 사람 손이 아니라 자동으로 작동하는 구조여야 한다. 그 구조를 고르는 것이 이 설계 결정이다.

2.문제점

  • 작은 LLM은 시킨 대로 따르는 것이 불안정하다. 판정은 "초과 — 늦춰라"인데 문장은 "속도를 올려요"가 나오는 일을 프롬프트만으로는 막을 수 없다.
  • LLM이 없는 상황이 일상이다. 모델을 아직 받지 않았거나, 응답이 늦거나 실패해도 코칭은 끊기면 안 된다.
  • 안전이 걸린 순간이 있다. 위험할 정도로 심박이 높을 때의 권고는 LLM이 늦거나 잘못 말할 여지를 허용할 수 없다.
  • 통제가 실제로 작동했는지 나중에 확인할 수 있어야 하고, 사용자도 직접 개입할 수 있어야 한다.

한 줄

구조

규칙이 방향과 사실 숫자를 확정하면 LLM은 그 재료로 문장만 만든다. 나온 문장은 형식, 방향, 숫자 세 가지 검사를 거치고, 걸리거나 LLM이 실패하면 "속도 줄이기" 같은 짧은 문구로 바꿔 내보낸다. 위험 심박 권고는 LLM을 거치지 않고, 모든 호출의 경로와 기각 사유가 기록된다

심박, 페이스 같은 상황을 프롬프트로 주면 LLM이 무엇을 권할지까지 스스로 판단해 문장을 만든다. 통제는 프롬프트에 규정을 써 두고 출력에 금칙어, 수치 범위 필터를 거는 방식이다. LLM 활용 서비스의 주류 접근이다

DP2. 설계결정 및 근거

3

1.최종 채택 구조

후보 1: 규칙 확정 + LLM 표현 한정 아키텍처 채택

2.채택 근거

  • 개입할 곳이 구조에 있다. 어긋난 문장의 기각(교정), 설정 토글과 폴백(보완), 위험 시 LLM 우회(안전전환)가 각각 구조에 존재하고 자동으로 작동한다. 2안의 개입은 프롬프트 수정뿐이고 그 효과는 보장되지 않는다.
  • 약한 모델이라는 전제와 맞는다. 1안은 LLM이 규정을 안 지켜도 통제가 성립한다 — 출력을 규칙이 다시 검사하고, 걸리면 바꿔 내보낸다. 2안은 "지켜 준다"는 기대 자체가 통제의 근거다.
  • 실패해도 코칭이 이어진다. LLM이 없거나 실패했을 때 1안의 최악은 "짧은 문구 코칭"이고, 2안의 최악은 "코칭 중단"이다.
  • 통제 작동을 데이터로 확인한다. 어떤 문장이 왜 기각됐고 언제 폴백했는지가 세션마다 기록되어 리포트에서 확인할 수 있다.
  • DP1과 서로 떠받친다. 판단을 규칙에 두는 같은 구조가 설명의 충실함(DP1)과 통제권(DP2)을 동시에 만든다.

3.보완 계획

  • 단기: 방향위반 기각율 등 측정 항목의 시뮬/단위테스트 층위 실측은 완료했다(검증 파트 QA3 수록 — 기각율 100%). 남은 것은 실주행에서의 기각률/폴백 사유 분포 수집과 검사 기준 조정이다. 방향 검사의 알려진 비대칭(유지 의도는 금지어 목록 검사만)도 같은 기록으로 감시한다.
  • 장기: 통제 구조를 유지한 채 코칭 상황(임무 종류)을 늘려, 판단을 위임하지 않고 코칭 내용의 자유도 상한을 완화한다.

Appendix. DP2 상세 설계 내역

A

A1.문제점이 걸리는 품질 속성

  • 작은 LLM은 시킨 대로 따르는 것이 불안정하다 → 제어가능성
  • 실시간이라 출력마다 사람이 검수할 수 없다 → 제어가능성
  • LLM 미가용, 지연, 오류가 정상 운영 범위다 → 강건성
  • 위험 심박 권고는 지연과 오작동을 허용할 수 없다 → 제어가능성(안전전환)
  • 통제가 작동했는지 사후 확인이 필요하다 → 제어가능성(감사)
  • 사용자도 개입할 수 있어야 한다 → 제어가능성(교정, 보완)
  • 통제가 과하면 표현이 굳는다 → 기능적응성

A2.채택안의 통제 장치 5층 (각 층은 독립 작동 — 한 층이 뚫려도 다음 층이 막는다)

층하는 일제어 유형
1. 격리판단은 규칙, LLM은 문장만 — 맡기는 권한 자체를 좁힌다예방
2. 출력 검사형식(길이), 방향(판정과 모순이면 기각), 숫자(관측에 없는 숫자면 기각)교정
3. 폴백걸리거나 실패하면 "속도 줄이기" 같은 짧은 문구로 바꿔 내보낸다안전전환
4. 안전 분리위험 심박 권고는 LLM을 거치지 않는다안전전환
5. 사람 개입 + 기록말하기 테스트로 판정 기준 정정, 설정 토글, 모든 호출 경로와 기각 사유를 세션에 기록교정, 보완, 감사

A4.예상 질문

  • "프롬프트를 잘 쓰면 2안도 통제되지 않나?" → 프롬프트 규정은 권고이지 강제가 아니다. 물론 2안에도 규칙 판정기를 병렬 검증기로 붙일 수는 있다 — 그러나 그 검증기가 곧 규칙 판정이고, 불일치 때 규칙을 따라야 하는 순간 1안 구조로 수렴한다. 2안 고유의 것은 "규칙 없이 LLM만 믿는 구간"인데, 그 구간이 통제되지 않는다.
  • "검사가 정상 문장까지 기각해 코칭이 굳지 않나?" → 가능하다. 그래서 기각이 전부 기록되고, 기각률이 높으면 기준을 데이터로 조정한다. 기각의 비용은 덜 자연스러운 짧은 문구이지 코칭 중단이 아니다.

A5.용어 대조(심사용)와 근거 문헌

개입 가능성 = intervenability(ISO/IEC 25059 제어가능성의 핵심) / 맡기는 일 자체를 좁히는 통제 = architectural containment(구조적 격리) / 실패 시 무손상 전환 = fail-safe fallback / 사람 개입 = HITL(루프 안 교정), HOTL(루프 위 감독) / 사후 확인 = audit(감사)

근거 문헌: ISO/IEC 25059(제어가능성 정의) / LLM 가드레일 계층 방어 서베이(구조적 격리가 가장 강한 층) / LLM 단독 판단 회피 권고 / 소형 모델 지시 이행 한계(이행률 60% 미만 사례)
