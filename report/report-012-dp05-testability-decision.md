## 슬라이드 1 — DP5. 설계 문제 정의

### 1. 배경

- 이 시스템은 검증하기 어려운 조건을 여럿 겹쳐 갖고 있다. 진짜 Zone 2 경계의 **정답지가 없고**, 입력이 실제 달리기에서만 나와 **같은 러닝을 두 번 뛸 수 없으며**, 워치와 폰 두 기기가 결합돼 있다.
- 그런데 판정, 개인화, 코칭 로직은 개발 중에 계속 바뀐다. 바뀔 때마다 실제로 뛰어야 확인이 된다면 검증은 사실상 안 하게 된다.
- 그래서 **실제로 뛰지 않고도 전 파이프라인을 반복 검증할 수 있는 구조**를 고르는 것이 이 설계 결정이다.

### 2. 문제점

- **자극을 재현할 수 없다.** 같은 심박 곡선을 두 번 만들 수 없으니 수정 전후를 같은 조건에서 비교할 수 없다.
- **위험한 시나리오를 만들 수 없다.** 위험 심박, 신호 두절 같은 중요한 상황은 실주행으로 만들기 어렵거나 위험하다.
- **변경마다 실주행이면 검증이 생략된다.** 변경 하나의 검증 비용이 러닝 한 번이면 자동화가 불가능하다.
- **시뮬에는 함정이 있다.** 시뮬을 만든 가정으로 시뮬을 채점하면 "정확하다"는 결론이 정의상 나온다. 시뮬의 역할 한계를 정직하게 그어야 한다.

## 슬라이드 3 — DP5. 설계결정 및 근거

### 1. 최종 채택 구조

**후보 1: 소스 추상화 + 폐루프 시뮬 계측 아키텍처 채택**

### 2. 채택 근거

- **재현이 검증의 전제다.** 수정 전후를 같은 자극으로 비교할 수 없으면 회귀를 잡을 수 없다. 1안은 시나리오 재생으로 이것을 얻는다.
- **위험한 것일수록 시뮬로 검증해야 한다.** 위험 심박에서 안전 규칙이 작동하는지를 실주행으로 확인하는 것은 위험하다. 시뮬 주입이 이 검증을 안전하게 만든다.
- **변경 비용이 러닝 한 번이면 검증은 생략된다.** 자동 회귀(몇 초)와 실주행(시간 단위)의 차이는, 로직이 계속 바뀌는 단계에서는 검증을 하느냐 마느냐의 차이다.
- **수렴은 압축 시간으로만 확인된다.** 개인화가 경계값으로 수렴하는지는 여러 세션에 걸친 동작이라 실측이면 수 주가 걸린다. 진짜 값을 아는 가상 러너의 폐루프가 이것을 분 단위로 만든다.
- **자기 채점 함정을 구조로 피했다.** 시뮬의 역할을 "구조 검증과 디버깅"으로 명시해, 시뮬 성적을 정확도 주장에 쓰는 함정을 설계 차원에서 차단했다. 실제 사람에 대한 정확도는 실주행 검증 계획으로 남긴다.

### 3. 보완 계획

- **단기**: 가상 러너 시나리오(두절 패턴, 경계 근처 진동)를 강건성 지표 측정과 연동해 확장한다.
- **장기**: 실주행 데이터를 수집해 시뮬이 답하지 못하는 실제 정확도를 검증하고, 시뮬 가정과 실측의 차이를 기록해 시뮬의 신뢰 범위를 갱신한다.

## Appendix 슬라이드 — DP5 상세 설계 내역

**문제점이 걸리는 품질 속성**

- 같은 자극을 두 번 줄 수 없다 → 테스트가능성(재현 주입)
- 위험/엣지 시나리오를 실주행으로 못 만든다 → 테스트가능성, 강건성
- 변경마다 실주행 검증은 비용이 감당 불가 → 테스트가능성(자동 회귀)
- 정답지가 없어 "정확하다" 채점 불가 → 시뮬 역할을 구조 검증으로 한정
- 개인화 수렴 확인이 수 주 걸린다 → 테스트가능성(압축 시간 폐루프)
- 워치-폰 결합이라 단독 실행이 어렵다 → 테스트가능성(기기 의존 분리)
- 시뮬 자산도 만들고 유지해야 한다 → 수행효율성(비용의 정직한 인정)

**채택안의 검증 구조 4요소**

| 요소 | 하는 일 |
|---|---|
| 1. 소스 추상화 | 실센서/가상 러너/수동 시뮬이 같은 인터페이스로 꽂힌다 — 검증과 운영이 같은 코드 경로 |
| 2. 폐루프 가상 러너 | 진짜 경계값을 아는 러너가 코칭에 반응 — 수렴을 분 단위에 정량 채점 |
| 3. 순수 로직 분리 | 결정 로직이 기기 의존 없는 모듈 — 단위 테스트 146개 자동 회귀 |
| 4. 시뮬 계측 | 시나리오 주입(경사/더위/두절/위험 심박)과 상태 관찰, LLM 켬/끔 비교 |

**QA 별점 종합**

| 품질 속성 | (1안) 소스 추상화 + 시뮬 계측 | (2안) 실기기 결합 검증 |
|---|:---:|:---:|
| 테스트가능성 | ★★★★★ | ★★ |
| 강건성 | ★★★★ | ★★ |
| 기능적응성 | ★★★★★ | ★★★ |
| 설명용이성 | ★★★★ | ★★★ |
| 수행효율성 | ★★★★ | ★★★★ |
| 기능정확성 | ★★★★ | ★★★★ (실환경 충실) |

**평가의 조건**: 이 별점은 1인 개발, 정답지 없음, 잦은 로직 변경, 위험 시나리오 포함이라는 이 과제 조건에서의 평가다. 두 안은 배타적이지 않다 — 1안에서도 실기기는 결합 확인과 최종 실주행 검증을 맡는다. 테스트 러너와 장비를 갖춘 조직이라면 실주행 비중이 커질 수 있다.

**예상 질문**

- "시뮬로 통과한 게 무슨 의미가 있나?" → 시뮬이 답하는 것은 "로직이 설계대로 동작하는가"이지 "실제 사람에게 정확한가"가 아니다. 후자는 실주행 검증으로만 답해지며 그 계획이 별도로 있다. 이 한계를 설계 문서에 못 박았다.
- "추상화 계층은 과한 설계 아닌가?" → 인터페이스 하나로, 자동 회귀 146개와 위험 시나리오 검증과 수 주짜리 수렴 확인의 분 단위 압축을 산다. 비용 대비 산 것이 크다.

**용어 대조(심사용)**: 입력 자리를 인터페이스로 = Ports and Adapters(헥사고날), 의존성 역전(DIP) / 실물을 대신하는 가짜 = test double / 출력이 입력에 되먹임 = closed loop / 수정 후 자동 재확인 = regression test / 시뮬과 실환경의 간극 = sim-to-real gap

**근거 문헌**: ISO/IEC 25010(테스트가능성 정의) / Cockburn(포트와 어댑터) / Meszaros(테스트 대역) / 테스트 피라미드(Cohn, Fowler) / 이 저장소의 자체 이력(시뮬 자기 채점 함정을 직접 확인하고 시뮬 역할을 한정 — 실험 기록 §15-3)
