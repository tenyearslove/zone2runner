# 실기기 결합 검증 아키텍처 컴포넌트 카탈로그 (설계 B)

- **상태**: 검토용 v1 (2026-07-31). 테스트가능성 DP의 **대안(설계 B)** 아키텍처를 우리 것과 **같은 방식**으로 식별/서술한다. 이는 우리가 구현한 게 아니라, 공정 비교를 위한 **가정 설계**(추상화 없는 직결 + 실주행 중심 검증)다.
- **도식**: `images/dp-05-testability-counter-detailed.png`(상세) + `images/dp-05-testability-counter-simple.png`(축약).
- **핵심 대비(우리 vs 카운터)**: 우리는 입력이 인터페이스(RunSource) 뒤에 있어 시뮬 소스로 갈아끼워 재현 검증하고, 카운터는 **센서가 파이프라인에 직결**돼 검증이 실기기 실주행에만 의존한다.

---

## A. 앱 구조

### A1. 센서 직결 파이프라인
- **표준 매핑**: 추론 서비스 / **책임**: Health Services/GPS API 호출이 판정/코칭 로직에 직접 연결 — 간접 계층 없음(구조 단순, 오버헤드 0). **우리와 차이**: 로직이 센서 API에 묶여 있어 센서 없이(개발 머신/CI) 실행할 수 없고, 테스트용 입력을 꽂을 지점이 없다.

### A2. 로직-플랫폼 결합
- **표준 매핑**: (구조 특성) / **책임**: 판정/개인화/분석이 앱 컴포넌트(Activity/Service) 안에서 플랫폼 API와 함께 동작. **우리와 차이**: 우리는 결정 로직이 안드로이드 의존 없는 순수 모듈이라 JVM 단위 테스트가 돈다 — 여기선 로직 검증에도 기기가 필요하다.

## B. 검증 절차 (실주행 중심)

### B1. 테스트 계획/코스 선택
- **책임**: 검증할 시나리오를 코스/날씨/컨디션 선택으로 근사(오르막 검증 = 오르막 코스). **우리와 차이**: 위험 심박/두절/경계 진동은 코스 선택으로 만들 수 없거나 위험 — 방어 로직이 미검증으로 남는다.

### B2. 실주행 수행
- **책임**: 실기기(워치+폰)를 착용하고 실제 달리며 기능 확인. 실환경 충실도 100%(2안의 강점 — 센서 특성/타이밍/OS 제약까지 실제). **우리와 차이**: 같은 자극을 두 번 줄 수 없어 수정 전/후 비교가 통계 비교로 흐려지고, 변경 하나의 검증 비용이 러닝 한 번이다.

### B3. 로그 수집/수동 분석
- **책임**: 세션 기록을 내려받아 수동 검토. **우리와 차이**: 관찰이 사후 로그에 한정 — 우리는 시뮬 대시보드에서 실시간으로 자극을 조작하며 상태(판정/가드/코칭)를 관찰한다.

### B4. 개인화 수렴 확인 (달력 시간)
- **책임**: 수 주간 실사용으로 경계 수렴을 관찰. **우리와 차이**: 참임계를 모르므로 "수렴했는지"를 체감으로 판단 — 우리는 참임계를 아는 가상 러너로 수렴 오차를 분 단위에 정량 측정한다.

## 요약 — 무엇이 다른가

| 축 | 우리 (설계 A: 소스 추상화 + 시뮬 계측) | 카운터 (설계 B: 실기기 결합 검증) |
|---|---|---|
| 입력 원천 | 인터페이스 뒤(실센서/시뮬 교체) | 센서 직결(교체 지점 없음) |
| 자극 재현 | 시나리오 재생(동일 자극 반복) | 불가(매번 다른 러닝) |
| 회귀 검증 | 자동(순수 모듈 단위 테스트, 수 초) | 수동(변경마다 실주행) |
| 엣지/위험 시나리오 | 시뮬로 안전하게 주입 | 만들기 어렵거나 위험 |
| 수렴 검증 | 참임계 폐루프, 분 단위 | 수 주 실사용, 체감 판단 |
| 실환경 충실도 | 시뮬 한계 있음(sim-to-real 간극) | 100% — 이 축은 카운터 우위 |
| 검증 인프라 | 시뮬 자산 구축/유지 필요 | 불필요 — 이 축은 카운터 우위 |
