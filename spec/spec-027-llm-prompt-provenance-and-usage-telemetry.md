# Spec-027: LLM 프롬프트 프로비넌스 + 사용 텔레메트리

- **상태**: Approved (2026-07-16) / Implemented
- **날짜**: 2026-07-16
- **관련 문서**: `spec/spec-005`(LLM 코칭 생성), `spec/spec-023`(설명 서비스 — 1회 생성/저장/재호출 없음), `spec/spec-007`(세션 기록/리포트), `arch/adr-002`(방향=규칙/표현=LLM), `arch/adr-026`(Nano Rewriting/Summarization), `arch/dp/dp-01-explainability`(provenance = 신뢰 메커니즘)

## 목표

1. **프롬프트 프로비넌스**: LLM(Gemini Nano)이 생성한 모든 문장에 대해 "그때 LLM에 무엇을 넣었나(프롬프트/입력 원문), 어떤 경로로 나왔나(엔진/폴백 사유), 얼마나 걸렸나"를 **생성 시점에 기록해 영속화**하고, 사후에 리포트에서 조회할 수 있게 한다. 코칭 히스토리의 각 문장을 터치하면 그 문장의 프로비넌스가 팝업으로 뜬다.
2. **사용 텔레메트리**: 세션 중(실시간)과 세션 후(리포트)에 LLM을 얼마나 썼는지 — 호출 수/성공 대 폴백/지연시간/입출력 크기/앱 프로세스 메모리 스냅샷 — 를 관측해 보여준다.

## 배경/원칙

- **DP-01(설명용이성)의 확장**: 이 시스템은 화면의 모든 수치에 대해 출처(provenance)를 답할 수 있게 설계돼 있다(관측/학습/설계 구분). 그러나 **LLM이 만든 텍스트**는 지금까지 출처(프롬프트)가 휘발됐다 — `LlmCoach.lastPrompt`가 직전 1건만 메모리에 들고 있고 저장하지 않는다. 텍스트에도 수치와 같은 provenance 규율을 적용한다.
- **spec-023 모델과 정합**: LLM 생성은 세션 종료 시 1회(스토리/개인화 설명) 또는 세션 중 이벤트 시(코칭)이고 이후 재호출이 없다. 따라서 **생성한 그 시점에 프롬프트를 함께 저장**하면 이후 조회는 저장본만 읽으면 된다(LLM 재호출 없음 유지).
- **없는 숫자 금지(제1원칙) 적용 — 자원 측정의 정직한 한계**: Gemini Nano 추론은 우리 앱 프로세스가 아니라 **Google AICore 시스템 서비스(별도 프로세스)** 에서 실행된다. 따라서 **추론 자체의 CPU/메모리는 앱에서 관측 불가**하고, 지어내지 않는다. 앱에서 실제로 관측 가능한 것만 기록한다:
  - **관측 가능**: 호출별 벽시계 지연(ms), 호출 수/경로(성공 대 폴백 사유), 프롬프트/출력 크기(자), 호출 직후 **앱 프로세스** PSS 메모리(KB, `Debug.getPss`).
  - **관측 불가(기록 안 함)**: AICore 프로세스의 CPU/메모리. 개발 중에는 `adb shell dumpsys meminfo com.google.android.aicore` 등 외부 도구로만 확인 가능하다(엔지니어링 절차, 앱 기능 아님).

## 범위

**포함**:
- LLM 호출 기록 구조(`LlmCallRecord`)와 세션 단위 수집기(`LlmCallLog`, 단일 기록 관문).
- 기록 대상 = 앱의 모든 LLM 경로: 실시간 코칭(`LlmCoach.say` — Nano Rewriting 톤 재작성/Prompt API/규칙 폴백 전 경로), 자유 생성(`LlmCoach.freeform` — 세션 스토리 폴백/개인화 설명/Zone2 설명 팝업), 세션 스토리 요약(`NanoSummarizer`). 규칙 폴백으로 끝난 호출도 기록(폴백 사유 = 프로비넌스의 일부).
- `RunReport.llmCalls` 영속화(SessionStore JSON) + 코칭 문장과 1:1 정렬(코칭 1문장 = coach 기록 1건).
- 리포트 UI: 코칭 로그 각 줄 터치 → 프로비넌스 팝업. "이번 러닝 이야기" 카드 터치 → 스토리 프로비넌스. "LLM 사용" 텔레메트리 카드 신설.
- 프로필의 개인화 설명(LearnedZone 저장)에도 생성 프롬프트를 함께 저장, 터치로 조회.
- 실시간: 시뮬 대시보드의 프롬프트 디버그 뷰에 누적 사용량(호출/폴백/평균 지연) 표기. 필드 로그(JSONL) coach 이벤트에 경로 추가.

**제외**:
- AICore 프로세스의 CPU/메모리 수치화(관측 불가 — 위 원칙).
- 토큰 수(온디바이스 API가 토큰 카운트를 노출하지 않음 — 문자 수로 대체, 정직 표기).
- 세션 간 누적 집계 대시보드(세션별 기록이 영속화되므로 필요 시 후속 확장으로 충분).
- 워치(LLM은 폰 전용).

## 기능 명세

### FR1 — 기록 구조와 단일 관문

```
LlmCallRecord(
  tSec: Int,        // 세션 경과 초(세션 종료 후 생성분 = durationSec)
  purpose: String,  // coach | story | personalization | zone2-explain
  engine: String,   // nano-rewrite | nano-prompt | nano-summarize | rule
  path: String,     // 상세 경로/폴백 사유 — 예: "llm(톤 재작성)", "rule(방향 기각)", "rule(LLM 미가용)"
  prompt: String,   // LLM에 실제로 준 입력. 재작성=규칙 원문, 요약=article, 프롬프트=프롬프트 전문. 규칙 경로면 ""
  output: String,   // 최종 채택 출력(출력 가드 통과 후)
  tookMs: Long,     // 호출 벽시계 지연
  appPssKb: Int,    // 호출 직후 앱 프로세스 PSS(KB). -1=미측정(테스트 등)
  facts: String,    // (2026-07-24 확장) 이 코칭의 근거 관측 요약 — 판정/지속심박/개인 경계/경사/페이스/케이던스/기온/트리거(CoachEvidence). 구버전 세션=""
)
```

- **`LlmCallLog`** = 세션 단위 수집기(순수 조립, GRASP Pure Fabrication). 스레드 안전(코칭 코루틴/스토리 코루틴 동시 기록). 모든 LLM 경로가 여기에만 기록한다(기록 책임의 단일화 — 진입점 4곳이 분산돼 있어 관문을 코드 이동 없이 '기록 싱크'로 통일).
- `LlmCoach`가 생성자에서 선택적으로 `LlmCallLog`를 받아 `say`/`freeform`의 **모든 귀결 경로**(재작성 성공/Prompt 성공/각 폴백)를 1건씩 기록. `NanoSummarizer` 호출부(세션 스토리)는 호출부에서 기록.
- PSS 측정은 주입 함수(`pssKb: () -> Int`)로 받아 JVM 단위테스트에서 Android 의존 없이 검증 가능(기본 -1).

### FR2 — 코칭 문장 1:1 프로비넌스

- `LlmCoach.say` 1회 = coach 기록 1건. `RunEngine.recordCoaching`의 코칭 라인과 **순서/개수가 일치**(코칭 생성은 `coachJob` 가드로 동시 1건이므로 순서 보장).
- 리포트 코칭 로그에서 i번째 줄 터치 → `llmCalls`의 purpose=coach i번째 기록 팝업: 경로/엔진/지연/**근거 데이터(그 순간의 관측 스냅샷)**/프롬프트(입력 원문)/출력. 개수 불일치(구버전 세션)면 "프롬프트 기록이 없는 세션"으로 안내(하위호환).

### FR3 — 세션 스토리/개인화 설명/팝업 프로비넌스

- 세션 스토리: Nano 요약 시도(prompt=article) → 실패 시 Prompt 자유 풀이(prompt=SessionExplainer.prompt) 각각 기록. 스토리가 비동기(세션 저장 후)로 확정되므로, 확정 시 `SessionStore.updateLlmCalls`로 세션 JSON의 llmCalls를 최신 스냅샷으로 갱신.
- 개인화 설명: `LearnedZone`에 설명과 함께 **생성 프롬프트/경로도 저장**(`explainPrompt`). 프로필 화면에서 설명 터치 → 프로비넌스 팝업. (규칙 폴백이면 "규칙 생성 — LLM 미사용"으로 표기.)
- Zone2 설명 팝업(러닝 화면): 세션 중이면 세션 로그에 기록(purpose=zone2-explain). 세션 밖 팝업은 저장할 세션 파일이 없어 기록하지 않는다(한계 명시 — 팝업 자체가 일회성 표시).

### FR4 — 사용 텔레메트리

- **리포트 "LLM 사용" 카드**(세션 후): 총 호출 수, LLM 채택 대 규칙 폴백 수(폴백 사유별), 용도별 내역, 평균/최대 지연, 프롬프트/출력 총 문자 수, 앱 PSS 스냅샷(최근). ⓘ 설명에 AICore 관측 한계를 정직하게 명시.
- **실시간**(세션 중): 시뮬/디버그 프롬프트 뷰에 "LLM n회 / 폴백 m회 / 평균 x ms" 누적 카운터. (라이브 화면은 러닝 집중 유지 — 실시간 상세는 디버그 뷰와 JSONL.)
- **필드 로그(JSONL, spec-012)**: coach 이벤트에 `path` 추가(기존 tookMs에 더해). 사후 분석은 세션 JSON(llmCalls)이 정본.

## 수락 기준 (AC)

- **AC-1 (프로비넌스 완전성)**: 세션 종료 후 저장된 JSON에서, 코칭 로그의 모든 줄에 대해 purpose=coach 기록이 같은 개수/순서로 존재하고, LLM이 표현한 줄은 prompt가 비어 있지 않다.
- **AC-2 (조회)**: 리포트에서 코칭 줄 터치 시 해당 줄의 경로/프롬프트/출력/지연이 팝업으로 표시된다. 스토리 카드/프로필 개인화 설명도 동일.
- **AC-3 (재호출 없음)**: 조회는 저장본만 읽는다 — 조회 시 LLM 호출 0회(spec-023 원칙 유지).
- **AC-4 (텔레메트리 정직성)**: "LLM 사용" 카드의 모든 수치는 앱이 실제 관측한 값(지연/카운트/문자 수/앱 PSS)만이며, AICore CPU/메모리 수치는 표시하지 않는다.
- **AC-5 (하위호환)**: llmCalls 없는 구버전 세션 JSON이 정상 로드되고, 리포트가 프로비넌스 없이 동작한다.
- **AC-6 (무영향)**: 기록 실패/미측정이 코칭/스토리 생성 자체를 막지 않는다(기록은 관측이지 게이트가 아님).

## 강의 프레임워크 매핑 (AI System / QA)

- **AI Operation Subsystem — 설명 서비스**: 프롬프트 프로비넌스는 설명 서비스의 입력 계보(lineage)를 텍스트 산출물까지 확장. **분석 서비스/Model Operation 모니터링**: 사용 텔레메트리는 운영 중 모델 사용의 관측(HOTL — 사람이 사후에 LLM 사용을 감사).
- **QA**: **설명용이성**(모든 LLM 산출물이 "무엇에서 나왔나"에 답함 — DP-01 provenance의 텍스트 확장), **제어가능성**(폴백 사유가 기록돼 가드레일 동작이 감사 가능), **수행효율성**(지연/호출량 관측 = 효율 QA의 측정 수단).

## 검증

- 단위: `LlmCallLogTest`(기록/스냅샷/통계/스레드 안전), `SessionCodecTest`(llmCalls 직렬화 왕복 + 구버전 하위호환).
- 통합: 시뮬 세션 1회 후 리포트에서 코칭 줄 터치 → 팝업 확인(실기기/시뮬 수동).
