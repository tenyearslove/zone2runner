# Spec-005: LLM 상황 코칭 생성

- **상태**: Draft
- **날짜**: 2026-07-01
- **관련 ADR**: `arch/adr-002-ondevice-llm-coaching.md`

## 목표

Zone 2 판정 결과와 실시간 맥락을 입력받아 자연스러운 코칭 멘트를 생성하고 TTS로 출력한다. 코칭 방향은 규칙이 결정하고 표현만 LLM이 담당한다(adr-002 대안 C).

## 범위

**포함**:
- 코칭 의도 결정 (규칙): Zone 상태 → 가속/감속/유지/독려
- 입력 컨텍스트: Zone 상태, 페이스 추세, 고도(오르막/내리막), SPM, 기온/날씨
- 프롬프트 구조: system(코치 페르소나 + 제약), user(구조화된 상황 + 의도)
- 출력 가드: 방향 일치 검증, 길이 제한, 금지 표현, 중복 쿨다운
- TTS 출력

**제외**:
- LLM 모델/런타임 선정 상세 (adr-002에서 유보)
- Zone 2 판정/개인화 (adr-013 / spec-004)
- HR 수집 (spec-003)

## 기능 명세

### 주요 흐름
1. 판정기가 Zone 상태 변화 또는 주기 트리거 발생
2. 규칙이 코칭 의도 결정 (예: 초과 → 감속, 미달 → 가속, 유지 → 독려)
3. 맥락(고도/페이스/SPM/날씨)을 구조화해 프롬프트 구성
4. On-device LLM이 한 문장 코칭 멘트 생성
5. 출력 가드 검증: 의도 방향과 멘트 방향 일치 확인, 실패 시 재생성 또는 템플릿 폴백
6. TTS 음성 출력

### 예외 처리
- LLM 지연/실패: 의도에 대응하는 템플릿 문구로 폴백 (QA4 제어가능성 — 폴백, QA6 수행효율성 — 무중단 보장)
- 방향 불일치 출력: 가드가 차단하고 폴백 (QA4 제어가능성 보장)
- 동일 상황 반복: 쿨다운으로 중복 안내 억제

## 모델 준비 (최초 실행 다운로드)

On-device LLM(Gemini Nano)은 최초 1회 모델 다운로드가 필요하다(**측정 ~4GB**, 수 분 소요). AICore가 관리하며 앱 간 공유된다(adr-007, 실기기 검증에서 확인).

- 앱 시작/코칭 준비 시 FeatureStatus 확인 후 분기:
  - **AVAILABLE**: 즉시 사용
  - **DOWNLOADABLE / DOWNLOADING**: **다운로드 진행 화면** 표시 (진행률, Wi-Fi 권장, 앱 포그라운드 유지 안내)
  - **UNAVAILABLE**: 폴백 경로 안내 (adr-007 Plan B 자체탑재 / Plan C 서버)
- **Graceful degradation**: 다운로드 중에도 핵심 기능(HR 판정 + 규칙/템플릿 코칭)은 동작하고, LLM 준비 완료 시 자연스러운 코칭으로 승격한다. → 모델 다운로드가 운동을 막지 않는다.
- 실패 시 재시도/나중에 정책, 셀룰러 데이터 다운로드 허용 여부는 사용자 설정.
- **⚠️ 포그라운드 전용 제약**: Gemini Nano 생성은 앱 포그라운드에서만 허용(ErrorCode 30, adr-007). 러닝 중 화면 끄고 주머니에 넣는 시나리오 대응(포그라운드 서비스/화면유지/폴백)은 확인/설계 필요 → 미해결.

## 수락 기준 (AC)
- [ ] AC-1: Zone 이탈 방향과 코칭 멘트 방향 일치율 95% 이상 (QA4 제어가능성 — 방향위반 기각)
- [ ] AC-2: 상황 변화 감지 후 음성 출력까지 5초 이내 (QA6 수행효율성)
- [ ] AC-3: LLM 실패 시 템플릿 폴백으로 코칭이 끊기지 않음
- [ ] AC-4: 네트워크 없이(오프라인) 코칭이 동작함
- [ ] AC-5: 최초 실행 시 모델 미보유면 다운로드 진행 화면을 표시하고, 다운로드 중에도 규칙/템플릿 코칭으로 운동이 가능함

## 미해결 사항
- [ ] 프롬프트 페르소나/톤 튜닝
- [ ] TTS 엔진 선택 (LLM warm ~2초 측정됨, adr-007 → TTS는 ~3초 내로 QA6 수행효율성 5초 예산 충족)
- [ ] 코칭 트리거 주기/쿨다운 값


## 부록: 케이던스(폼) 가이드 (2026-07-03 추가)

코칭 컨텍스트에 케이던스(spm)를 추가하고, 범위 밖일 때 방향 문구에 폼 가이드 한 문장을 덧붙인다.

- **근거**: 걸음 빈도를 +5~10% 올리면 무릎/고관절 부하가 유의미하게 감소 — Heiderscheit et al.,
  "Effects of Step Rate Manipulation on Joint Mechanics during Running", Med Sci Sports Exerc 2011;43(2).
  체계적 리뷰: Schubert et al., Sports Health 2014. 준거 ~180spm은 Daniels의 엘리트 관찰(Daniels' Running Formula).
  "보폭을 줄이고 빈도를 올리는" 방향이 부상 예방 관점의 주류 권고(고케이던스 해악은 합의 약함).
- **기준**: LOW < 162spm(180의 -10%) → "부상 예방을 위해 보폭은 줄이고 발걸음은 더 자주".
  HIGH > 190spm → "발걸음 빈도는 살짝 낮추고 보폭을 편안하게"(부드럽게, 합의 약한 영역).
- **방향 잠금과의 관계**: 폼 가이드는 페이스 방향과 별개 축 — DirectionGuard는 폼 절
  (발걸음/케이던스/보폭/스텝/걸음 ~ 구두점)을 제외하고 방향을 판정한다. 따라서 방향 표현은
  반드시 폼 절 밖에 위치해야 한다(RuleCoach 문구 규약).
- **데이터 소스**: spm은 판정 특징(feat[4])이기도 함 — 워치 실측(ExerciseClient STEPS_PER_MINUTE,
  Data Layer /spm) 우선, 미수신 시 페이스 기반 추정 폴백. 파생 표시: 보폭(m) = 속도/케이던스
  (라이브 타일 + 리포트 평균 보폭).
